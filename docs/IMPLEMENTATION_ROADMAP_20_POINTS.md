# UniWeb implementation roadmap — 20 points

**Purpose:** One execution tracker for the One Merchant Console blueprint and the related master-plan and audit requirements.
**Planning date:** 2026-10-28
**Web launch target:** December 2026, conditional on release gates and partner readiness.
**Rule:** A point is complete only when its acceptance checks pass in code and the required environment/live checks have evidence. A smoke-test pass alone does not certify a point or production readiness.

### Point statuses

- **Partial** — relevant code or UI exists, but acceptance evidence is incomplete.
- **Not verified** — no reliable code or live evidence is recorded yet.
- **Blocked externally** — requires owner, partner, provider, legal, or production environment action.
- **Complete** — every acceptance check for that point has evidence; no blanket completion from a related feature.

### Locked product exclusions and release gates

- No customer-fund custody, no consumer PPI wallet/top-up, no silent merchant settlement deduction, no guessed/forced partner routing, and no false “sent”, “accepted”, “verified” or “LIVE” claim.
- Card/net-banking use the partner-hosted page when supported. Existing merchant accounts must not be duplicated where partner terms do not allow it.
- BNPL/PayPal and any other provider connector require actual contract/provider approval; multi-country availability requires per-country legal and operational review. The registry tracks approval; it cannot grant it.
- Live Route/Split API remains parked unless the owner explicitly requests it and its separate partner/commercial gates are passed; market-comparison and white-label reference plans do not override the approved delivery order.
- December 2026 means a limited, evidence-backed web MVP only if the release gates and partner dependencies are satisfied. Android/iOS/Windows are later clients, after API stability; a worldwide all-partner launch is not a one-month commitment.

## Work order and exit gates

Work in ID order, finishing one point before moving to the next unless a dependency requires a documented parallel prerequisite. A point may be declared complete only with:

1. Requirement-to-code trace and acceptance tests.
2. No unresolved critical/high defect in that point.
3. Relevant environment or provider evidence; label unavailable checks as **blocked**, not passed.
4. Documentation and operations instructions updated.
5. Explicit status update in this file: evidence, date, and any owner/partner action still required.

No database migration is to be applied to a live environment without explicit owner authorization. A partner registry entry alone does not mean a partner has accepted UniWeb, granted credentials, approved the business model, or enabled production processing.

## Schedule and launch reality

- **20 points are work packages, not equal-sized calendar units.** Several contain provider, legal, security, or production dependencies.
- A **December 2026 limited web launch** may be achievable only as a deliberately scoped MVP, if critical security, KYC privacy, checkout, reconciliation, monitoring, rollback and at least one contracted/verified partner are ready. This is a target, not a guarantee.
- A complete worldwide platform with every partner, every payment rail, and Android/iPhone/Windows apps is **not responsibly promiseable within one month**. Launch by country and partner after local legal, commercial, technical and security approval. Plan native clients after the web/API contract stabilizes.
- Partner participation is not automatic. Each provider can require contracts, KYB, security review, approved use of APIs/merchant-owned credentials, certifications, support/SLA, webhook testing and production approval. The registry records and gates these facts; it cannot grant them.
- Product constraints remain: no customer-funds custody, no consumer PPI wallet/top-up, no guessed partner route, no fake “sent/ready/live” status, and no public claim of worldwide legal availability without country-by-country review.
